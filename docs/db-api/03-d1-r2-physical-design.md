# D1・R2 物理設計方針

## 1. 文書の目的

本書は、現行の SQLite スキーマとマイグレーション `000001`〜`000027` を維持したまま、その論理構造を Cloudflare D1・R2 の独立した検証環境で匿名化・合成データにより再現するための物理設計方針を定める。

本書は物理設計方針を定義する文書であり、本書内では SQL、Go 実装、Cloudflare リソース作成を実施しない。実作業の開始可否は `04-migration-plan.md` の「8. 実装開始条件」に従う。記載するテーブル追加・制約強化は候補であり、論理モデル、API 契約、既存データの実態を確認してから確定する。

Cloudflare は検証先であり、最終稼働先は AWS、最終 DB は RDS for PostgreSQL で確定している。D1・R2 固有仕様をドメイン層へ漏らさず、DB とオブジェクトストレージを交換できる構造を必須とする。

## 2. 設計の前提

- 現行 `000001`〜`000027` は履歴として不変とし、修正・並べ替え・再採番しない。
- 新規の空 D1 には、既存履歴をそのまま再生するのではなく、最終状態を表す D1 用 baseline を適用する。
- 稼働中 SQLite を更新する必要がある変更は `000028` 以降として追加する。
- `000028` 以降の各論理変更には、SQLite 用・D1 用・AWS RDS PostgreSQL 用の物理 migration を個別に用意し、同一の論理版として manifest で追跡する。これらを D1 baseline へ含めない。
- 金額、数量、状態遷移、承認、採番の業務規則はこの設計作業では変更しない。
- DB と R2 の間に分散トランザクションはないものとして設計する。
- `schema-diagram.html` の `APP_DATA` は `01-mock-logical-model.md`、現行との差分は `02-difference-matrix.md` を根拠とする。モック資料内の READ/WRITE、状態、正本の矛盾は推測で確定せず、未確定事項として扱う。

## 3. 現行スキーマから引き継ぐ規則

### 3.1 識別子

- 現行の主キーは TEXT 型のアプリケーション生成 ID である。
- D1 検証でも ID 形式を維持し、DB 自動採番への置換は行わない。
- 外部公開番号と内部 ID を分離する。
  - 内部 ID: 不変の主キー
  - 商品コード、伝票番号、リクエスト ID: 組織内で一意な業務番号
- AWS 移行時も同じ ID を保持し、D1 と AWS の相互検証を可能にする。

### 3.2 金額・為替・数量

- 金額は最小通貨単位の符号付き整数で保持する。
- 金額列名は既存どおり `_minor` を基本とし、通貨列と組にする。
- JPY の場合も整数の最小単位として扱い、浮動小数点型を使用しない。
- 為替レートは既存の `rate_scaled` を維持し、倍率を設定値または契約で明文化する。
- 数量は INTEGER とし、対象業務に応じて正数または 0/1 の CHECK を維持する。
- Workers/JavaScript 境界では 64 bit 整数を `Number` に無条件変換しない。API では安全範囲を保証するか、文字列として受け渡す。

### 3.3 日時

- 保存日時は UTC の RFC3339 文字列に統一する。
- 日付のみの業務項目は `YYYY-MM-DD` とする。
- 比較・並べ替え可能性を保つため、同種の列で精度とタイムゾーン表記を統一する。
- 表示時だけ Asia/Tokyo へ変換する。
- DB の現在時刻関数に依存せず、Clock 抽象を通してアプリケーションが値を供給する。

### 3.4 状態・真偽値

- 状態値は TEXT とし、既存の CHECK 制約を baseline に反映する。
- 真偽値は INTEGER の `0` / `1` に統一し、CHECK 制約を付ける。
- 状態追加は DB、API、UI、監査ログの影響を同時に確認してから行う。

### 3.5 論理削除

- 商品の `deleted_at` など既存の論理削除規則を維持する。
- 物理削除を前提とする CASCADE は原則追加しない。
- R2 オブジェクト削除は DB の論理削除とは非同期に実施できるようにする。

## 4. テナント境界

### 4.1 必須規則

- テナント所有データには `organization_id` を持たせる。
- すべての読み書きで認証コンテキストの `organization_id` を条件に含める。
- API から任意の `organization_id` を受け取って権限判定に利用しない。
- 業務番号の一意制約は原則 `(organization_id, business_number)` とする。
- 索引の先頭列は、主要アクセスパターンに応じて `organization_id` とする。

### 4.2 現行で要確認の境界

次の子テーブルは組織を親から間接的に継承する、または単一 ID の外部キーだけで参照先組織との一致を保証している。

- `purchase_slip_lines`
- `stocktake_lines`
- `market_import_rows`
- 組織列を持ちながら、参照先が同一組織であることを複合外部キーで保証していない各種明細・関連テーブル

D1 用 baseline では現行互換を優先する。境界強化は `000028` 以降の候補とし、既存データに組織不一致がないことを検証してから以下を選択する。

1. 子にも `organization_id` を追加し、複合 UNIQUE と複合外部キーで保証する。
2. 親経由の所有関係を維持し、全クエリを親との JOIN でスコープする。
3. D1 の制約互換性が不足する場合は、条件付き更新とアプリケーション検証を併用する。

テナント境界をアプリケーション検証だけに依存する状態は最終形としない。

## 5. 正規化候補

以下は移行前に確定せず、データ実態と画面仕様を確認してから `000028` 以降で扱う。

### 5.1 商品属性とマスタ

現行商品ではブランド、素材、駆動方式、BOX、付属品等の一部を TEXT で保持する。画面表示のスナップショットとして必要な文字列と、検索・入力制御に使うマスタ参照を分ける候補とする。

- マスタ参照用 ID
- 伝票・公開時点を保持する表示名スナップショット
- 自由入力が許される項目

既存文字列を失わないよう、ID 追加後にバックフィルし、未対応値は「その他」へ強制変換せず監査対象として残す。

### 5.2 付属品

検索や複数選択を行う場合は、商品と付属品マスタの中間テーブルを候補とする。現行 `accessories` 文字列は互換表示またはスナップショットとして一定期間維持する。

### 5.3 購入依頼グループ

現行 `request_group_id` は複数商品の依頼を束ねる識別子だが、グループ自体の親レコードがない。購入者、備考、依頼日時、全体状態を親へ置く `purchase_request_groups` 相当の導入を候補とする。

### 5.4 JSON

承認スナップショット、修正履歴、CSV 原文、マスタ詳細等の JSON は、次の分類を行う。

- 監査・再現用で検索しない JSON: JSON のまま保持
- 絞り込み・結合・制約に使う値: 列または関連テーブルへ正規化
- API 一時ペイロード: 永続化の必要性を再確認

JSON を維持する場合は、アプリケーションでスキーマバージョンと妥当性を検証する。D1 の JSON 関数だけへ依存しない。

### 5.5 意図的に維持する非正規化

次は履歴の再現性を目的とするため、原則としてスナップショットを維持する。

- 仕入明細の商品属性
- 売上・出荷時の取引先情報
- 仕入返品時の仕入先表示
- ゲスト公開時の商品・画像情報
- 承認申請時の対象内容
- 伝票修正前後の JSON

## 6. 制約設計

### 6.1 必須制約

- 主キー、NOT NULL、業務番号 UNIQUE
- 金額・数量の非負または正数 CHECK
- 状態、通貨、真偽値の CHECK
- 外部キー
- 予約、承認待ち、棚卸下書き等の排他を守る部分 UNIQUE

### 6.2 追加候補

- `(organization_id, id)` の複合 UNIQUE とテナント一致外部キー
- JSON 文字列の妥当性
- `created_at <= updated_at` 相当の整合性
- R2 オブジェクトキーの組織内一意性
- 画像の `sort_order` の商品内一意性

D1 で利用する CHECK、部分索引、トリガー、ALTER TABLE の互換性は実環境で先に適合試験する。未確認の機能を baseline の必須要件にしない。

### 6.3 監査ログ

- 現行の UPDATE・DELETE 禁止を維持する。
- D1 のトリガー互換性を検証する。
- アプリケーションの監査書込みと DB トリガーの役割を分ける。
- 保持期間、AWS へのアーカイブ、個人情報マスキングを別途決定する。

## 7. 索引設計

### 7.1 原則

- 索引は実際の WHERE、JOIN、ORDER BY に基づいて作る。
- テナント内検索では `organization_id` を先頭に置く。
- 一覧は状態と日付の複合索引を優先する。
- 外部キー列は JOIN 頻度を確認して索引する。
- UNIQUE 制約が生成する索引との重複を避ける。
- 低選択性の真偽値だけの索引は作らない。

### 7.2 初期 baseline

現行の47索引を起点とし、次を実データ相当件数で測定する。

- 在庫一覧: 組織、在庫状態、仕入日、商品コード、SKU、シリアル
- 伝票一覧: 組織、日付、状態、取引先
- 承認一覧: 組織、状態、申請日時
- 棚卸: 組織、状態、棚卸日、差異確認状態
- 購入依頼: 組織、グループ、状態、商品
- ゲスト公開: 組織、会社、BOX、商品、並び順

D1 ではクエリプランと実行時間を採取し、未使用索引・不足索引を migration で調整する。

## 8. 同時実行と冪等性

- 商品コード採番は「読み取り後に加算」ではなく、競合を検出できる原子的更新を使う。
- 承認、予約、在庫状態、伝票確定は「期待する現在状態」を更新条件に含める。
- API の書込みにはリクエスト ID または冪等キーを使用する。
- UNIQUE 違反は内部エラーではなく、競合として安全に再試行または利用者へ通知する。
- ローカル SQLite の単一接続で発生しにくかった競合を D1 で負荷試験する。

## 9. R2 オブジェクト設計

### 9.1 責務分離

- R2: 画像等のバイナリ本体
- D1: 所有者、関連商品、状態、表示順、検証済み属性、監査情報
- API: 認可、アップロード状態遷移、署名付きアクセス、整合性回復

R2 custom metadata を業務データの正本にしない。

### 9.2 オブジェクトキー

推奨形式:

`{environment}/{organization_id}/products/{product_id}/{image_id}/original.{extension}`

- 環境と組織を必ず分離する。
- 利用者が送信したファイル名をキーへ直接使用しない。
- 同じキーを上書きせず、画像 ID またはバージョンを変える。
- 変換画像を作る場合は `variants/{variant_name}.{extension}` のように分離する。

### 9.3 D1 画像メタデータ候補

現行 `product_images` を起点に、次を候補とする。

- `id`
- `organization_id`
- `product_id`
- `storage_provider`
- `bucket_name`
- `object_key`
- `object_version` または `etag`
- `checksum_sha256`
- `original_name`
- `content_type`
- `size_bytes`
- `width`
- `height`
- `sort_order`
- `upload_status`
- `uploaded_by`
- `created_at`
- `ready_at`
- `deleted_at`

`storage_provider` は `r2`、将来の `s3` 等を表す。アプリケーションは provider 固有 URL ではなく `image_id` を扱う。

### 9.4 二段階アップロード

1. API が認可し、D1 に `pending` メタデータを作成する。
2. API またはクライアントが R2 へアップロードする。
3. サイズ、MIME、checksum を検証する。
4. 条件付き更新で D1 を `ready` にする。
5. 失敗時は `failed` とし、期限超過 `pending` と孤児オブジェクトを回収する。

D1 登録と R2 PUT の順序を問わず中間障害があり得るため、各段階を冪等にする。

### 9.5 読取り・公開

- bucket は private を基本とする。
- 管理画面は認証・認可後に短時間 URL または Worker 経由で配信する。
- ゲスト公開は公開スナップショット単位の認可規則を適用する。
- `guest_box_published_images` は、公開時点の画像が後から変化しないよう immutable object/version を参照するか、公開専用オブジェクトへコピーする。

### 9.6 削除・回復

- UI 上の削除では先に D1 を論理削除する。
- R2 物理削除は再試行可能な後続処理とする。
- D1 だけ、R2 だけに残ったデータを検出する整合性監査を用意する。
- バックアップ復元時に D1 と R2 の基準時点が異なる場合の再リンク手順を定義する。

## 10. D1 baseline と追加 migration

### 10.1 D1 baseline

D1 baseline は次の条件を満たす単一の最終形スキーマとして管理する。

- `000001`〜`000027` 適用後と論理的に同じ構造
- `000020` の交換レート一時テーブルを含まない
- `000023` のプレビュー用 seed を含まない
- テーブル、索引、トリガー、CHECK、UNIQUE、外部キーを明示
- baseline 自体に版番号と生成元の legacy migration 範囲を記録

baseline は既存 SQLite DB には適用しない。

### 10.2 `000028` 以降の候補

番号は論理変更単位で確定し、以下を一つの巨大 migration にまとめない。

- テナント境界強化
- R2 画像メタデータ拡張
- 付属品の正規化
- 商品属性とマスタ参照の整理
- 購入依頼グループ親テーブル
- JSON スキーマバージョン
- 冪等リクエストまたは非同期処理状態

各変更は、SQLite 用 migration、D1 用 migration、AWS RDS PostgreSQL 用 migration で同じ論理版を追跡できるよう manifest を持つ。manifest には、モック（M）・レビュー追加仕様（R）・現行実装（C）の出典、決定 ID、P0 未確定事項への依存、後方互換性と既存データへの影響を必須記録する。

## 11. Cloudflare と AWS の交換可能性

### 11.1 アプリケーション境界

Go のドメイン・サービス層から以下を interface として分離する。

- Repository / Unit of Work
- Transaction runner
- ObjectStore
- SignedURLProvider または MediaReader
- Clock
- ID generator
- Idempotency store

D1 の HTTP/binding、SQLite の `database/sql`、AWS のドライバ型をドメイン型へ露出させない。

Cloudflare 検証環境の D1 adapter は、Go から業務ユースケース別の内部 Worker API だけを呼び出す。任意 SQL、任意テーブル名、任意条件を受け取る API は作らない。複数更新を伴う一つの業務トランザクションは一回の Worker request 内で開始から commit または rollback まで完結させ、複数 request を一つのトランザクションとして扱わない。

### 11.2 DB 方言

- 共通 SQL の範囲を優先する。
- SQLite/D1 固有の PRAGMA、部分索引、トリガー、RETURNING 等は dialect capability として隔離する。
- AWS の最終 DB は RDS PostgreSQL とし、型、真偽値、日時、JSON、UPSERT、プレースホルダ差異を adapter 内で吸収する。
- Repository 契約テストを SQLite、D1、RDS PostgreSQL で共通実行する。

### 11.3 Storage

- `ObjectStore` は Put/Get/Delete/Head と必要最小限の署名 URL 操作を定義する。
- R2 の ETag と S3 の version ID を同一概念として誤認しない。
- DB には provider、bucket、key、provider version、checksum を分けて保存する。
- URL を永続化しない。

## 12. 確定済み前提と残る未確定事項

- 確定済み: AWS の最終 DB 製品は RDS for PostgreSQL を採用する
- 未確定: `schema-diagram.html` / `APP_DATA` に残る READ/WRITE、状態、販売先・ゲスト会社等の正本の矛盾
- 未確定: PostgreSQL のメジャーバージョン、Multi-AZ 構成、接続プール方式、RTO/RPO。AWS staging の負荷・復旧試験後に確定する
- session / CSRF の保存先
- 監査ログの保持期間とアーカイブ
- R2/S3 の公開方式と URL 有効期間
- 公開画像を参照固定にするか複製するか
- 画像変換、最大寸法、checksum、ウイルス検査要件
- JSON の検索要件
- テナント複合外部キーを全テーブルへ適用する範囲
- D1 の実環境で使用可能な SQLite 機能
- 既存データ中の組織不一致、孤児行、非正規化文字列の品質

## 13. 設計確定条件

次を満たすまで、本番 baseline の確定・適用、`000028` 以降の migration の確定・適用、実データ移行 SQL、本番用 D1 Service Worker API の実装へ進まない。`04-migration-plan.md` 8.1 の読み取り専用診断、interface 定義、合成データを使う使い捨て capability test、baseline 候補生成・差分出力は除く。

- APP_DATA を含む論理モデルとの突合完了
- 全既存 migration 適用後スキーマとの一致確認
- テナント境界方針の承認
- 金額・日時・ID 契約の承認
- D1 capability test の合格
- R2 の二段階処理と回復手順のレビュー完了
- AWS 交換可能性レビュー完了
- 移行・復旧計画の承認
