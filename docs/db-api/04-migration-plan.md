# SQLite から D1・R2 への移行計画

## 1. 目的と対象

本書は、現行 SQLite とローカル画像ファイルを読み取り専用の参照元として調査し、匿名化・合成した検証用データだけを Cloudflare D1・R2 へ投入して適合性を確認するための計画である。現行の業務データおよび本番秘密情報は Cloudflare へ移行しない。

Cloudflare は最終稼働先ではなく、AWS 移行前の検証先とする。そのため、D1・R2 への移行完了をもってデータ層設計を固定しない。

対象:

- 現行 migration `000001`〜`000027` 適用後の論理スキーマ
- 現行業務データから生成した匿名化データ、または独立した合成データ
- `product_images` とローカル画像ファイルの形式を再現した合成画像
- ゲスト公開画像スナップショットを再現する合成データ
- 制約、索引、トリガー、監査情報

対象外:

- 新規 API の実装
- 業務ロジック変更
- 認証、承認、採番、在庫状態遷移の仕様変更
- AWS 本番移行の実行
- 請求書等、現行で永続ファイル要件が確認できないデータの独自追加

## 2. 移行原則

- 現行 `000001`〜`000027` を変更しない。
- 原本 SQLite とアップロードディレクトリを読み取り専用で保全する。
- 変換は再実行可能かつ冪等にする。
- 移行中の全件数、金額、参照関係、ファイル checksum を記録する。
- 不正データを黙って補正・破棄しない。
- D1 と R2 への接続切替は Cloudflare テスト URL 内だけで、検証合格後に行う。
- 現行運用環境、本番 DNS、本番書込み先は変更しない。
- テスト切替失敗時は Cloudflare テスト URL を停止し、現行環境には影響させない。
- D1/R2 固有 ID や URL を業務データへ混入させない。
- 本番・実データ（匿名化前）は、承認の有無にかかわらず本計画では Cloudflare へ持ち込まない。現行データ由来の検証データは、Cloudflare 投入前に不可逆匿名化し、個人・取引先・認証情報・シリアル番号を再識別できないことをレビューで確認する。

## 3. 移行資産

### 3.1 スキーマ資産

- legacy migrations: `000001`〜`000027`

- post-baseline migrations: `000028` 以降
- schema manifest:
  - 論理バージョン
  - SQLite migration
  - D1 migration
  - 将来の AWS migration
  - 出典（M: モック、R: 追加仕様、C: 現行実装）
  - 決定 ID
  - P0 未確定事項への依存
  - 後方互換性・既存データへの影響
  - 適用条件
  - rollback / forward-fix 方針

### 3.2 データ資産

- テナント、利用者、権限、設定
- セッション、CSRF
- 監査ログ
- マスタ
- 商品、画像メタデータ、在庫イベント
- 仕入、売上、出荷、返品、棚卸
- 承認、予約、購入依頼
- 相場、為替、CSV取込履歴
- ゲスト企業、BOX、公開スナップショット、認証情報

### 3.3 ファイル資産

- 商品画像本体
- 画像メタデータ
- ゲスト公開画像が参照する元画像

## 4. フェーズ構成

### フェーズ0: 前提資料の確定

作業:

- `01-mock-logical-model.md` と `02-difference-matrix.md` が参照する `schema-diagram.html` / APP_DATA の版と更新日時を確定する。
- 現行 SQLite の版、ファイルパス、アップロードディレクトリを確定する。
- 最終 AWS DB は RDS for PostgreSQL として記録し、エンジンのメジャーバージョン、
  Multi-AZ 構成、接続プール方式、RTO/RPO は AWS staging の試験項目として分離する。
- データ保持・個人情報・監査ログ要件を確認する。

完了条件:

- 論理モデルと現行スキーマの差分一覧が承認されている。
- 移行対象・対象外が確定している。

### フェーズ1: 現行データ診断

読み取り専用で次を採取する。

- 全テーブルの件数
- migration 適用履歴
- 主キー重複
- UNIQUE 重複候補
- 外部キー違反と孤児行
- 組織列と参照先組織の不一致
- CHECK 制約外の状態・通貨・真偽値
- NULL、空文字、日付形式、UTC 表記の品質
- 金額・数量の最小、最大、合計
- JSON の妥当性とスキーマ版
- 商品画像メタデータと実ファイルの対応
- DBにないファイル、ファイルがないDB行
- 画像サイズ、MIME、拡張子、checksum

出力:

- 診断レポート
- 補正が必要なデータ一覧
- 自動補正、手動判断、移行除外の分類

完了条件:

- 未解決の P1 データ不整合がない。
- 補正規則が承認されている。

### フェーズ2: D1 capability test

本番データを使わない検証用 D1 で以下を確認する。

- transaction / batch の境界
- 外部キーの有効化と検証
- CHECK、UNIQUE、複合外部キー
- 部分 UNIQUE 索引
- 監査ログの更新・削除禁止トリガー
- ALTER TABLE の対応範囲
- query planner と索引利用
- 最大SQLサイズ、変数数、batch件数
- エラーコードと再試行可能性
- 同時実行時の競合
- バックアップ、export、restore の手順

特に legacy `000020` のような PRAGMA とテーブル再構築は、D1 baseline では回避する。将来同種の変更が必要な場合の forward migration 手順だけを検証する。

完了条件:

- baseline に利用する全機能が D1 で実証されている。
- 非対応機能の代替設計が承認されている。

### フェーズ3: baseline と変換仕様

作業:

- legacy `000001`〜`000027` 適用後の最終スキーマを抽出する。
- 一時テーブルと preview seed を除外する。
- D1 baseline のテーブル・制約・索引・トリガー一覧を作る。
- 型変換表を作る。
- テーブルごとの抽出順、変換、投入順を定義する。
- `000028` 以降の新規論理変更は baseline に混ぜず、必ず post-baseline migration として分離する。

基本方針:

- 既存意味を変える正規化は後続 migration とする。
- D1 で必要な型・制約表現などの物理差分だけを legacy 最終形と同じ論理構造の baseline に取り込み、manifest に差分理由を記録する。
- ID、業務番号、監査時刻を維持する。
- seed は権限等の必須マスタとプレビューデータを分離する。

完了条件:

- 空 D1 に baseline を適用できる。
- legacy最終形とのスキーマ比較結果が説明可能である。

### フェーズ4: R2 合成画像投入

作業:

1. ローカル画像は読み取り専用で形式、MIME、サイズ分布だけを診断する。
2. 実画像を含まない合成画像と checksum manifest を作成する。
3. D1 に検証用 `pending` メタデータを準備する。
4. 組織別 object key で合成画像を R2 へ PUT する。
5. Head/Get により size、content type、checksum を照合する。
6. D1 メタデータを `ready` にする。
7. 合成したゲスト公開スナップショットの参照を検証する。
8. orphan / missing 一覧を作成する。

再実行規則:

- 同じ image ID と checksum は成功済みとしてスキップする。
- 同じ key で checksum が異なる場合は上書きせず競合として停止する。
- `pending` のまま期限超過した行は調査後に再開または削除する。
- R2 にだけ存在する object は manifest と照合し、即時削除しない。

完了条件:

- 全合成画像が `ready` または承認済み除外である。
- checksum 不一致がない。
- 公開スナップショットが意図した画像を参照する。

### フェーズ5: D1 合成データ投入

匿名化・合成データの推奨投入順:

1. 組織
2. 権限・ロール
3. 利用者・設定
4. 仕入先・マスタ・ゲスト企業/BOX
5. 仕入伝票・仕入明細
6. 商品・画像メタデータ・在庫イベント
7. 為替・相場
8. 売上・出荷・割当
9. 購入依頼・予約
10. 承認
11. 棚卸
12. 返品
13. revision・公開スナップショット
14. セッション・CSRF・監査ログ

セッションと CSRF は移行せず全利用者を再ログインさせる選択肢もある。採用には認証要件の承認が必要で、移行処理が独自判断しない。

投入方法:

- テナント単位、テーブル単位の小さな batch
- batch ID、開始/終了時刻、投入件数、失敗件数を記録
- 再投入時に重複を生まない UPSERT/skip 方針
- 外部キー無効化を常態化しない
- 大量テーブルは日付または主キー範囲で checkpoint を持つ

完了条件:

- 全 batch が成功または承認済み除外。
- D1 内の制約検証が合格。

### フェーズ6: オフライン整合性検証

#### 構造

- テーブル、列、型、NULL、既定値
- 主キー、外部キー、UNIQUE、CHECK
- 索引、部分索引、トリガー

#### 件数

- 全件数
- 組織別件数
- 状態別件数
- 日付別件数

#### 集計

- 仕入、売上、返品、相場の金額合計
- 商品の在庫状態別件数
- 予約数、承認待ち数
- 棚卸の理論値、実数、差異
- 伝票明細数とヘッダ集計値

#### 参照

- 全外部キー
- 組織境界
- 売上と出荷の割当数量
- 返品元伝票と返品商品
- ゲスト公開と商品・画像

#### ファイル

- D1 ready 行と R2 object の一対一対応
- size、MIME、checksum
- 代表画像の表示
- private/public 認可

判定:

- P0/P1 不一致は切替不可。
- P2 は影響、回避策、修正期限を記録し承認が必要。

### フェーズ7: アプリケーション互換試験

DB/Storage adapter を実装する別フェーズで、同一の契約試験を実行する。D1 adapter は Go から外部公開されない業務別 D1 Service Worker API を呼び出し、任意 SQL を送信しない。一つの業務トランザクションは一回の Worker request 内で完結させる。

- SQLite adapter
- D1 adapter
- R2 adapter
- 将来の AWS DB adapter
- S3 adapter

確認対象:

- 一覧、検索、詳細、登録、修正
- 状態遷移と競合
- 承認・差戻し
- 採番
- CSV取込
- 画像アップロード・表示・削除
- 空データ・大量データ
- エラー変換
- 冪等再送

完了条件:

- 既存業務機能の回帰試験が合格。
- provider 固有値がドメイン/APIレスポンスへ漏れていない。

### フェーズ8: リハーサル

本番相当の件数・分布を再現した匿名化または合成データで以下を計測する。本番データ、本番 secret、個人を再識別できる値は使用しない。

- export 所要時間
- 変換所要時間
- D1 import 所要時間
- R2 upload 所要時間
- 検証所要時間
- 差分同期所要時間
- ロールバック所要時間

少なくとも2回実施し、同じ手順で同じ結果になることを確認する。

完了条件:

- 許容停止時間内に収まる。
- 手順書を別担当者が再現できる。

### フェーズ9: Cloudflare テスト環境内の切替リハーサル

推奨手順:

1. Cloudflare テスト利用者へテストデータの変更凍結を通知する。
2. Cloudflare テスト環境だけの書込みを停止する。
3. 合成データのテスト用バックアップと manifest を採取する。
4. 最終差分の合成データと合成画像を投入する。
5. オフライン整合性検証を実施する。
6. smoke test を実施する。
7. Cloudflare テスト URL の接続先だけを D1/R2 adapter へ切り替える。
8. 監視を開始する。
9. 判定責任者が開放を承認する。

現行運用環境、本番 DNS、本番書込み先は変更しない。旧テストDBと新テストDBへの同時書込みは、整合性保証と再送設計が完成していない限り採用しない。

### フェーズ10: 安定化

- エラー率、レイテンシ、競合、D1 query、R2失敗を監視する。
- 件数・主要集計を定期照合する。
- orphan object / missing object を定期監査する。
- Cloudflare の旧テスト環境は保持期限まで読み取り専用で保全する。
- AWS 移行に使える問題・変換規則を記録する。

## 5. 復旧計画

### 5.1 テスト切替前

- 合成テスト用 SQLite DB の整合性確認済みバックアップ
- 合成画像ディレクトリのスナップショット
- DB・ファイル checksum manifest
- アプリケーション版と設定の保存
- 復旧手順の実地確認

### 5.2 切替判定

次の場合は Cloudflare テスト URL での D1/R2 開放前に中止し、旧テスト環境を継続する。

- 件数・金額・参照関係の P0/P1 不一致
- 画像 checksum 不一致
- 認証またはテナント分離の不具合
- 採番、承認、在庫状態遷移の回帰
- 復旧手順が機能しない

### 5.3 テスト開放後ロールバック

D1/R2 のテスト開放後に合成データへの書込みが発生した場合、次のいずれかを事前に選ぶ。この手順で破棄対象にできるのは合成テストデータだけであり、実データには適用しない。

1. 短い検証窓では書込みを制限し、問題時は合成データへの全新規操作を破棄して旧テスト環境へ戻す。
2. D1 の変更ジャーナルから旧形式へ逆変換してから戻す。
3. 問題機能だけ停止し、D1/R2 上で forward fix する。

選択肢2は逆変換の実装・試験なしに採用しない。`000012`〜`000018` に down migration がないため、DB schema は原則 forward fix またはバックアップ復元で回復する。

### 5.4 R2 回復

- DB rollback だけで R2 object を即時削除しない。
- 移行 batch ID または manifest で移行物を識別する。
- 復旧後、参照されない object を隔離期間経過後に削除する。
- ゲスト公開 URL の無効化手順を用意する。

## 7. AWS 最終移行への引継ぎ

D1/R2 検証で次を成果物として残す。

- provider非依存の論理スキーマ
- D1 baseline と migration manifest
- 抽出・変換・検証仕様
- データ品質問題と補正履歴
- Repository / ObjectStore 契約試験
- R2 object manifest と checksum
- 性能、制限、競合、障害の計測結果
- D1固有回避策の一覧

AWS ではこれらを使い、DB 方言と Storage adapter だけを置換する。D1のPRAGMA、エラーコード、HTTP batch、R2 URLやETagをAWS設計へ直接持ち込まない。

## 8. 実装開始条件

### 8.1 直ちに着手できる非破壊作業

- 現行 SQLite と画像ディレクトリの読み取り専用診断
- legacy `000001`〜`000027` の最終状態、checksum、manifest の作成
- モック（M）・追加仕様（R）・現行実装（C）の DTO マッピング
- Repository、Transaction、ObjectStore の port/interface 定義
- 現行 SQLite/filesystem adapter の特性テストと契約テスト
- 使い捨て D1/R2 と合成データによる capability test
- D1 baseline 候補の生成と legacy 最終形との差分出力（適用はしない）

capability test 用の fixture SQL は、使い捨ての検証用 D1 にのみ適用できる。本番 baseline、`000028` 以降の migration、実データ移行 SQL へそのまま転用してはならない。

### 8.2 承認まで保留する作業

- `000028` 以降の最終確定と既存 SQLite への適用
- D1 baseline の確定および検証用 D1 への適用（8.1 の候補生成・差分出力を除く）
- 現行 DB、現行画像、実データへの書込みまたは移動
- 本番用 D1 Service Worker API の確定
- 実データの D1/R2 取込
- Cloudflare テスト URL の D1/R2 adapter への切替
- P0 未確定の業務状態、採番、承認、返品、公開スナップショットに依存する実装
- 本番データまたは本番 credential を使用する作業

API 契約は M/R/C の DTO マッピングと P0 未確定事項の決定が完了するまで固定しない。上記保留作業を開始するには、物理設計、データ診断、D1/R2 capability test、R2 object key、テナント境界、切替・復旧基準、AWS 交換可能性の各レビュー承認を必要とする。
